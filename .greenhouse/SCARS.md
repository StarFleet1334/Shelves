# SCARS

One line per thing that broke here and what got past it.
Every tending is handed the tail of this file before it starts, so
the same wall is not walked into twice.

- `node tests/harness.js 9` printed "all 0 scenarios passed" and exited 0 -> a number that names no scenario now FAILS, or a roadmap proof would tick itself before the test existed
- rung 1 returns for EVERY repo the moment ONE row carries chips -> the ladder must treat page chips as a floor and keep climbing for the rest (measured: 4 repos, 1 chipped, 3 shelved as Ungrouped with zero requests)
- a repo page that 429s or 404s is swallowed and the repo lands in Ungrouped with no warning, while the toolbar still says `via api (public)` -> count the unread and say so (P.IV)
- a 401 on `/user/repos` never retries the unauthenticated endpoint, yet the source line already says `api (public)` -> either fall back for real or stop claiming it
- topics scraped from a repo page must be scoped to `.Layout-sidebar`, or a README full of /topics/ links lies about the repo's tags
- a row's own textContent is read AFTER the note margin is appended -> every row matched the query "note" and a saved note counted twice; capture `li.dataset.shText` once, before anything is added to the row
- the filter forces shelves open to show hits, and the `toggle` listener wrote that to the collapse store -> a cleared search left every closed shelf hanging open; park the real state in `data-sh-was-open` and stand the listener down while `data-filtering` is set
- GitHub's <meta name="description"> is "<about>. Contribute to o/n development…" and there is no way to tell its joining period from one the owner typed -> strip it with the boilerplate; a stray "." on every description is the more visible wrong
- a proof that names a harness scenario by NUMBER ticks itself the moment a scenario is inserted above it (appending facts/find/note made `harness.js 8` mean the facts scenario, which passes) -> proofs name scenarios by keyword, and a selector matching nothing fails
- `.sh-margin { flex: 0 0 100% }` appended to GitHub's repo row: `d-flex` DOES NOT WRAP, so a 100% basis with flex-shrink 0 does not drop to its own line — it takes the width and refuses to give it back, collapsing the description from 599px/2 lines to 94px/13, breaking words mid-word -> put the note INSIDE the row's text column (the li child holding the h3), and give any li-level fallback `flex: 1 1 100%; min-width: 0`. jsdom cannot see this; tests/row-layout.html + aether/look.py can
- a shelf glyph the font stack lacks renders as the MISSING-GLYPH BOX, which at 10px looks enough like a hollow square marker to survive being looked at: `□` (U+25A1) and `●` (U+25CF) are both tofu in GitHub's own stack on Windows, and `●` was slot 0 -> measure every candidate against the width of U+FFFF (guaranteed to have no glyph anywhere); equal width IS the box. tests/glyph-probe.html
- a fixture that draws only the shelves this month happens to have draws only some of the palette: the first identity shot rendered 9 of 12 slots and the tofu was sitting in one of the 3 it never reached -> the fixture names twelve labels, which the collision walk guarantees exhausts every slot
- ONE lightness cannot serve two themes: at hsl(H, 62%, 52%) blue measured 3.3:1 on #0d1117 while yellow measured 2.2:1 on #ffffff, because luminance is not a function of hue -> solve each hue for its own lightness at a common relative luminance (0.19), which clears 4.3:1 on both. This extension has no theme detection on purpose, so the colour has to work on both backgrounds rather than pick one
- reporting a topic family's reach as the SUM of its spellings inflates it: `ai-project` (2) + `aiproject` (1) is three repos, not four, when one repo wears both -> count the union of repo indices, or a labelling problem reads as a bigger collection
- a gap counted over every repo reports the SOURCE's shape as the reader's failing: api.github.com's body carries no README, so "no README" over API-answered records is every repo on a token-holding account -> every finding declares the field it needs, and a repo whose source could not answer leaves the numerator AND the denominator (P.XIII). What could not be asked is printed, because a silently smaller denominator is its own lie
- one string served as both the button's word and the name of the set it selects: the button says SHOW, so the bar afterwards said "2 show of 5" instead of "2 no README of 5". Read fine in the code, nonsense on the page
- the repo-page chip lost its glyph for the leftovers shelf: the glyph was inside the branch that paints the colour, and the plain shelf has no colour BY DESIGN -> `Ungrouped` wore its dot on the shelf and nothing on the chip. Two drawings of one identity that disagree is the failure the whole system exists to prevent. Caught only in a real browser
- the background top-up was designed as a service worker + the `alarms` permission, which is the obvious shape and the wrong one: a worker cannot ride the session cookie, so it could only have warmed what the API already answers in ONE call — the expensive half is the private repos, and only a same-origin fetch from a github.com page can read those. Building it dropped a permission instead of adding one (P.VII)
- writing `shelfMap` from render() without adding it to main.js's QUIET list is a render -> storage change -> reload -> render loop
- a canary with no sample floor is a canary that gets turned off: below five pages read, a run of genuinely sparse repos is indistinguishable from a dead selector. And the fixture for it must NOT be an empty page — the failure worth catching is the one where the parse still returns something that looks right
- the repo-page chip staked the whole feature on two CLASS NAMES (`.Layout-sidebar`, `[data-testid=repository-sidebar]`) and neither matched the real logged-in page: no chip at all, beside an About panel plainly on screen. A class is the half of GitHub's markup that churns -> the class is a fast path and the finder is structural, climbing from the "About" heading to the first ancestor holding another sidebar landmark, bounded by "never an ancestor containing the <h1>" and "never wider than half the window"
- rendering nothing was the right ANSWER and the wrong silence: "GitHub renamed the sidebar", "the loaded extension is a stale build" and "this is not a repo page" all looked identical, and telling them apart cost a round trip through a human pasting DOM into a console -> mark.js now console.debug()s which of them it is, and says so again when it lands via a fallback
- CHARTER measurement 1 ("the profile list renders no topic chips") went stale under us: GitHub now renders them, so rung 1 answers and short-circuits. 77 repos resolved `via page` with 9 tagged and 68 silently Ungrouped for zero requests. A measurement is true on a date, not forever — the ones that "determine the entire architecture" are the ones to re-check
- nothing anywhere asked WHOSE profile was open: `isRepoTab()` tests the URL shape and the tab param, so a stranger's Repositories tab sent the reader's Bearer token to `/user/repos` (which answers with the READER's repos — useless on that page) and then scraped every one of the stranger's repo pages with the reader's session cookie. Measured: 12 repos, 12 authenticated fetches, 12 permanent cache entries; at 600 repos that is 600 requests for one click on a link -> the free rungs work anywhere, the expensive ones only on your own profile (P.XIV). "Cannot tell who is signed in" must count as YOURS, or a moved meta tag disables the extension for everybody at once
- `scrape()` — the highest-volume path in the extension, hundreds of authenticated same-origin fetches — was the ONLY one with no backoff, while warm.js, which makes six, had one. Measured against a server answering 429 to everything: 40 of 40 requests issued, and a page of Ungrouped repos with no explanation at all. The asymmetry was exactly backwards
- there was no cache eviction path ANYWHERE: an entry written once lived forever, and warm.js refreshes everything it finds, so a single visit to a stranger's 300-repo profile left the browser re-fetching somebody else's repositories for as long as the extension was installed. Prune generously (four TTLs, floor 90 days) or the top-up and the pruner fight each other
- two path segments went from a page-supplied href straight into `fetch("/" + name)`. The leading slash contains every crafted form to github.com — measured, no SSRF — but not WHICH github.com path: `/settings/tokens/x` resolved to an authenticated GET of the reader's token page, whose text was then cached and made searchable in their own UI. A contained capability is still a capability nobody asked for
- fixing a quadratic exposed an unbounded DOM behind it: with the pairwise scan gone, 9 000 topics resolved in 45 ms and returned 7 741 findings — 7 741 buttons with 7 741 listeners. An unbounded computation and an unbounded render are the same bug in different clothes, and the second one only becomes visible once you fix the first
- CHARTER said "never stores your repositories anywhere". True when the cache held topics; false from `facts.js` onward, which caches descriptions, README openings and private repo NAMES. A promise the code contradicts is worse than no promise — and the sentence most likely to go stale is the one written when the claim was easy to keep
- rows on the leftovers shelf stood tall with an empty band under two lines of text, and the first diagnosis was a GUESS DRESSED AS A MEASUREMENT: GitHub's sparkline arriving with a degenerate viewBox, "reproduced" at 87px -> 214px in a fixture written from that same guess, and fixed with `#shelves-host li svg { max-height: 32px }`. None of it was true of the page. The real fragment is `<svg width="155" height="30" aria-hidden="true">` — sized attributes, NO viewBox — and taking the ceiling back off the LIVE page changed the height of 0 of 54 rows. A fixture built from the hypothesis can only ever confirm it; the fixture has to be built from the page
- what it actually was: `.sh-margin[data-has="0"]`, the invisible pencil reserved on every note-less row. Measured on a real 54-repo profile — GitHub's own rows 109px, ours 131px, and switching off the empty marker put all 54 back to 109px exactly. 22px x 54 rows is 1 188px of blank. It reads as a bug ONLY on the leftovers shelf because a repo lands there for having no topics and usually has no description either, so 22px of nothing sits under a two-line row and the empty half is as tall as the full half; on a shelf whose rows carry a description and chips it is a tenth of the row
- and the reason it was reserved was right — a pencil appearing on hover grows the row and shoves every row below it under the cursor. The answer is not to make it conditional but to take it OUT OF FLOW: parked at `top: 100%` in the 24px of bottom padding the row already has. Scoped by `#shelves-host` (the repo-page chip has no row to park in), by `.sh-col` (the unrecognised-markup fallback appends to the <li>, where `top: 100%` is the next row) and by `[data-has="0"]` (a written note is content and belongs in the flow)
- a size complaint about a re-parented row still deserves the ancestry question first — moving their <li> from `#user-repositories-list > ul > li` to `... > #shelves-host > details > ul > li` does silently drop any rule of theirs written with a child combinator. It just was not the answer this time, and the way to tell is to strike our own rule out on the live page and see whether anything moves
- `flex-wrap: wrap` for the unrecognised-markup fallback was applied to EVERY row in the host, rewriting GitHub's own flex layout on the many rows whose margin sat safely in a text column -> scoped behind a `data-sh-loose` flag set only when the fallback actually fires
- writing `
` inside a bash heredoc to build a JS string literal collapses it to a REAL newline and breaks the file — twice now, in two different files, both times silently until node parsed it. Build JS through the Write tool or a script file, never through `python - << EOF` with escapes in it

- and the row-height bug the owner was actually reporting was NONE OF THAT, because it is invisible signed out and both sessions measured signed out: `fetchRestOfPages` imports rows from page 2..N, and GitHub's commit sparkline is a `<poll-include-fragment>` carrying a `data-nonce` from the response it was served in. Imported into this document it never reaches the network at all (measured on the live signed-in page: 30 requests for GitHub's own 30 rows, ZERO for the 47 merged) -> straight to `is-error`, which reveals the `data-show-on-forbidden-error` blankslate GitHub ships inside it. That blankslate is a full-width page element landing in a 145px column, so "Uh oh! There was an error while loading." wraps to about one character per line: 47 rows at 1 416px each, 70 431px of page against 9 171px once the fragments are dropped. It reads as BLANK because at that width nothing in it is legible
- the lesson under it: a logged-out profile is a DIFFERENT PAGE, not a cheaper sample of the same one. Private repos, star buttons and — the one that mattered — nonce-checked fragments only exist in the signed-in response. Two rounds of "measured in a real browser" were measured on a page the owner never looks at
- and an unpacked extension does NOT pick up an edited content script on a page reload; Chrome caches it until the extension itself is reloaded at chrome://extensions. A fix verified by injecting it into the live page is a verified fix; the same fix "verified" by reloading the tab is a measurement of the old build
